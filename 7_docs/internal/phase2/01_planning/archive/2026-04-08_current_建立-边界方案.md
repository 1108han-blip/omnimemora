- 禁止项
    
- 接口边界
    
- 仓库边界

那工程团队一定会顺手往“先跑通再说”的方向滑，最后就会变成：

- 云端先补个 `/memory/write`
    
- Railway 先连个 backend
    
- backend 没有，就再补一个 hosted backend
    
- 最后产品方向被“临时跑通逻辑”带歪
    

这很常见。

# 一、根因到底是什么

本质上是三件事没锁死。

## 1. 产品原则没有变成工程宪法

你心里知道“记忆不该上云”，但工程侧没有收到这种硬约束：

- 云端不得保存用户主记忆
    
- 云端不得依赖 hosted memory backend
    
- `/memory/*` 不得成为正式云产品能力
    

只要没写死，执行的人就会默认：  
**哪里方便，哪里先实现。**

---

## 2. 控制面和数据面没有做物理隔离

如果同一个仓库、同一套服务、同一批环境变量里同时出现：

- trial / billing / tenant
    
- memory write / search / snapshot
    
- backend url
    

那执行者一定会把它们视为同一系统里的“未完成模块”，而不是“禁止跨越的边界”。

结果就是职责混合。

---

## 3. 验收标准写成了“能跑通”，不是“不能越界”

很多项目翻车就翻在这里。

错误验收标准是：

- API 通了没
    
- write 能写吗
    
- search 能查吗
    
- demo 能演示吗
    

正确验收标准应该加一句：

- **是否把用户主记忆写进了云端**
    
- **是否引入了 hosted memory backend 依赖**
    
- **是否让云端承担了数据面职责**
    

没有这类“反向验收”，方向就会漂。

---

# 二、以后怎么控制：不是靠提醒，是靠制度

你要的是开发中不跑偏，那就不能靠“我再强调一次”，而要靠**五层约束**。

---

# 三、五层控制法

## 第 1 层：写死架构宪法

这个必须单独成文，而且放在所有仓库最上层。

文件名可以直接叫：

- `ARCHITECTURE_GUARDRAILS.md`
    
- 或 `PRODUCT_CONSTITUTION.md`
    

内容不要写虚的，就写硬规则：

### OmniMemora 架构宪法

1. 用户主记忆数据默认只存储在用户控制的本地或私有环境。
    
2. 云端产品不得承载用户主记忆存储与检索主链路。
    
3. 云端产品不得依赖 hosted primary memory backend 才能成立。
    
4. Cloud 仅负责控制面：鉴权、计费、租户、策略、控制台。
    
5. 任何云端 `/memory/*` 能力只能是内测、mock、demo 或未来可选能力，不能作为当前正式承诺。
    
6. 新增接口、服务、环境变量、数据库表时，必须标注其属于 control plane 还是 data plane。
    
7. 任何违反以上原则的 PR，一律视为架构违规。
    

这不是文档美化，这是红线。

---

## 第 2 层：仓库和目录物理切开

这是非常关键的一步。

如果你的云端仓库里还能看到这些目录：

- `memory/`
    
- `snapshot/`
    
- `vector_store/`
    
- `namespace_storage/`
    
- `backend_adapter/`
    

那迟早又会长回去。

你要强行拆成：

### 云端仓库

- `omnimemora-cloud-console`
    
- `omnimemora-cloud-gateway`
    

只允许出现：

- auth
    
- billing
    
- tenants
    
- entitlements
    
- policy bundles
    
- admin
    
- telemetry
    
- docs
    

### 本地/执行面仓库

- `omnimemora-local-engine`
    

才允许出现：

- memory write/search/read/delete
    
- namespace
    
- file storage
    
- indexing
    
- dedup
    
- snapshot
    
- recall
    

**边界不靠自觉，靠目录结构。**

---

## 第 3 层：环境变量白名单

这是最容易被忽视、但最有效的一层。

### 云端服务中禁止出现的变量

- `VIKING_URL`
    
- `MEMORY_BACKEND_URL`
    
- `PRIMARY_STORAGE_URL`
    
- `VECTOR_STORE_URL`
    
- `LOCAL_NAMESPACE_ROOT`
    
- 任意指向主记忆 backend 的变量
    

### 云端允许出现的变量

- `STRIPE_SECRET_KEY`
    
- `D1_DATABASE_ID`
    
- `OMNIMEMORA_ADMIN_TOKEN`
    
- `OMNIMEMORA_POLICY_BUNDLE_URL`
    
- `OMNIMEMORA_REGISTRY_SYNC_TOKEN`
    

也就是说：

**环境变量本身就要表达架构边界。**

只要云端还留着 `*_BACKEND_URL` 这种东西，工程师就会下意识继续往 hosted memory 方向补。

---

## 第 4 层：PR 模板里加入“越界检查”

以后每个改动都要过这一关。

PR 模板里加固定字段：

### Architecture Boundary Check

- 这个改动属于 Control Plane 还是 Data Plane？
    
- 是否新增了主记忆存储、检索、文件上传、snapshot 能力？
    
- 是否让云端依赖一个 memory backend？
    
- 是否引入了任何用户主数据落云？
    
- 是否违反 `PRODUCT_CONSTITUTION.md`？
    

如果回答不清楚，PR 不合并。

这个特别适合你现在的多 agent / 多模型协作环境。因为大模型最容易“好心办坏事”，你得让它先对边界表态。

---

## 第 5 层：验收加入“反向验收”

以后每个阶段验收，不光问“做成了什么”，还要问“有没有做错不该做的”。

### 正向验收

- trial 是否可开通
    
- billing 是否可用
    
- tenant 状态是否正常
    
- key 管理是否正常
    

### 反向验收

- 云端是否保存了用户主记忆
    
- 云端是否存在正式 `/memory/write/search/delete` 产品承诺
    
- 云端是否依赖 hosted memory backend 才能工作
    
- 仓库中是否又引入 memory plane 模块
    
- 文档是否暗示“云端托管记忆”
    

**真正防跑偏的，是反向验收。**

# 四、给你一个最实用的方法：先定义“禁止开发清单”

你这种项目很适合直接做一个 `FORBIDDEN_WORK.md`。

里面写：

## Cloud 侧禁止开发项

- Hosted primary memory storage
    
- Hosted namespace lifecycle
    
- Hosted file-backed memory snapshot
    
- Hosted vector indexing for user primary memory
    
- Cloud `/memory/write`
    
- Cloud `/memory/search`
    
- Cloud `/memory/read`
    
- Cloud `/memory/delete`
    
- Cloud `/memory/snapshot`
    
- Any required backend url for primary memory
    

这样 Codex、Claude Code、OpenClaw 在执行时都会有一个明确的“不许碰区域”。

# 五、为什么大模型执行时特别容易把你带偏

因为模型天然偏向三件事：

## 1. 补全缺口

看到 `/memory/search` 没有，就会觉得应该补。

## 2. 让链路跑通

看到 `backend_url` 不通，就会觉得应该再造一个 backend。

## 3. 追求局部闭环

看到 Cloudflare + Railway 没闭环，就会本能补成完整 SaaS。

但你的真实目标不是“局部功能闭环”，而是“**产品边界正确**”。

所以你以后给 Codex/CC 的任务，不能只写：

- 实现功能
    
- 补全接口
    
- 修复调用链
    

要改成：

- 在不引入 hosted memory plane 的前提下实现 X
    
- 禁止新增任何主记忆存储能力
    
- 如需补接口，仅限 control plane
    
- 若发现当前架构与宪法冲突，优先删除错位能力，而不是补齐
    

这句话特别关键。

# 八、最本质的一句话

**产品方向不是靠“想清楚”来守住的，是靠“让错误实现无法通过”来守住的。**

你这次跑偏，不是因为你没想清楚，恰恰是因为你想清楚了，但没有把它变成工程约束。

所以接下来别再口头强调“记忆在用户端”了。  
直接把它做成：

- 文档红线
    
- 目录红线
    
- 配置红线
    
- PR 红线
    
- CI 红线
    
- 验收红线
    

这样开发才不会自己长歪。
