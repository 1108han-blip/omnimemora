
**你现在要做的是“可控软上线”，不是“把整个项目公开”**。

所以先给总原则：

```text
代码不公开 ≠ 不能发安装包
软上线 ≠ 官网公开发布
真实用户验证 ≠ 先把云端全部做完
```

下面我一个个拆。

---

## 1）核心代码不能下发，安装包放在哪

先说结论：

**短期不要把核心代码仓库公开。安装包和源码是两回事。**  
你现在发的是**可运行 binary / installer**，不是发 repo。

这和你现阶段定位是吻合的：当前发布方式本来就应该是**10–50 用户、手动分发 binary**，而不是公开发布。

### 你现在最稳的放法

按优先级我建议这样：

### 方案 A：私有对象存储 / 私有文件分发链接

最适合你当前阶段。

可选思路：

- Cloudflare R2 私有链接
    
- GitHub Release 但仓库保持 private / 或单独建 release 分发仓
    
- Railway 不适合放安装包本体，它更适合跑服务，不适合做安装包分发主存储
    

你需要的是：

- 一个固定下载地址
    
- 能替换版本
    
- 能统计下载次数
    
- 最好能设置过期或人工控制
    

### 方案 B：doloclaw.com 做下载落地页，安装包放对象存储

这通常是你现在最合理的结构：

```text
doloclaw.com/download  →  按钮点击  →  跳转到私有/半私有安装包链接
```

这样做的好处：

- 官网只负责“解释和承接”
    
- 安装包不直接绑在主站代码里
    
- 后续换存储、换版本都轻
    

这也符合 Bootstrap Layer 的定位：下载、安装、启动是入口，但安装层不承担 metering / billing / UI 逻辑。

### 方案 C：手动私发

前 5–10 人可以直接这么干。  
最笨，但最可控。

适用于：

- 第一批熟人
    
- 第一轮排雷
    
- 不想让下载链接扩散
    

### 不建议你现在做的

- 不建议把核心 repo 公开后让用户自己 build
    
- 不建议把安装包直接塞进主代码仓大张旗鼓公开
    
- 不建议现在就做全自动公开下载页 + 全平台注册
    

因为你现在还在验证“产品是否成立”，不是扩大曝光。路线图里也明确了这一阶段是**limited release / 外部验证**，不是公开发布。

---

## 2）线上用户怎么取得

先说实话：

**你现在不需要“线上拉新”，你需要“高质量测试用户”。**

这两个东西完全不是一回事。

如果你现在去追陌生大流量，结果通常是：

- 安装率低
    
- 理解率低
    
- 噪音高
    
- 你根本不知道问题出在产品还是用户不匹配
    

### 你该找什么人

只找这一类：

```text
平时真的在用 Codex / Claude Code / 类似 agent 工具的人
并且对 token、上下文、成本、效率有感觉
```

这才是你的早期核心用户，不是泛 AI 用户。

### 获取路径，按效率排序

#### 第一层：你已有圈子

最值钱。

来源：

- 你认识的 Codex / Claude Code 用户
    
- AI 开发者群
    
- 独立开发者群
    
- 你项目相关交流群
    

这里转化率最高，因为他们至少理解使用场景。

#### 第二层：定向社区招募

不是广撒网，是定向发帖。

适合去的地方：

- AI coding 相关群
    
- 独立开发者社区
    
- GitHub / X / Discord / Telegram 里和 Claude Code、Codex、AI agent 相关的圈子
    

发帖不是“求用户”，而是：

```text
招 10–20 个 AI 重度用户做封闭内测
要求：平时真实用 Codex / Claude Code
回报：优先试用 / 直接交流 / 后续内测资格
```

#### 第三层：官网申请表单

这个可以做，但别指望马上来很多高质量用户。

官网只做一个简单入口：

```text
申请内测 → 留邮箱 / Telegram / X / 使用工具类型 / 每周 AI 使用强度
```

然后你人工筛。

### 不该现在做的事

- 不要跑大范围广告
    
- 不要做“所有 AI 用户都能用”的泛招募
    
- 不要为了人数把非目标用户塞进来
    

因为你现在要验证的是**产品-用户匹配**，不是流量能力。

---

## 3）云端 doloclaw.com、Railway、GitHub 里面的代码现在要不要对齐

结论很直接：

**要对齐“口径”和“版本边界”，但不需要现在把所有代码完全一锅端同步。**

也就是说：

### 必须对齐的，是这三件事

#### ① 对外定位

对外只能有一个说法：

- OmniMemora 是本地优先
    
- 默认本地 Runtime
    
- 云端可选
    
- 核心价值是 token savings / context optimization
    
- 当前是 limited release，不是正式公开版
    

这几个点在宪法、路线图、执行计划里都已经钉死了。

#### ② 版本号和发布物

如果你现在发的是 `v0.3.6`，那：

- doloclaw.com 文案要写 v0.3.6 soft launch
    
- 下载包要对应 v0.3.6
    
- GitHub release 也要对应 v0.3.6
    
- 变更说明只写这版真实具备的能力
    

#### ③ 用户路径

官网、安装包、dashboard、connect 命令、反馈入口，这一条路径要一致。

---

### 不必现在强行完全对齐的，是代码部署层

比如：

- Railway 上跑的是云端辅助服务
    
- GitHub 有主 repo、网站 repo、安装器 repo
    
- doloclaw.com 只是静态站
    

这些可以暂时分开，只要**版本认知一致**就行。

### 你现在最容易踩的坑

#### 坑 1：官网说一套，安装包是另一套

比如官网还在讲旧架构、云优先、或者别的名字。这个必须立刻清掉。

#### 坑 2：GitHub 暴露过时文档

如果公开仓里还是旧文档、旧品牌、旧路径，会直接伤信任。

#### 坑 3：Railway 上跑的东西和本地优先定位冲突

你的文案不能让用户以为“不联网就不能用”。因为 Local First 是基础宪法。

### 所以我的建议是

现在做一个**最小对齐清单**：

```text
A. 品牌统一：全改成 OmniMemora
B. 口径统一：本地优先 / 云端可选 / token savings
C. 版本统一：v0.3.6 soft launch
D. 下载路径统一：只有一个主入口
E. 反馈入口统一：只有一个回收点
```

先做这 5 项，够了。别现在花大力气重构所有线上仓库。

## 4）线上陌生用户如何走完测试全流程的每一步

这个问题本质上是：

**你怎么把“陌生人自助测试”设计成一个不会掉人的漏斗。**

先说实话：  
陌生用户不会替你“配合测试”。  
他只会在任何一个卡点直接流失。

所以流程必须变成**傻瓜式单线程**。

---

# 你要的不是“测试说明”，而是一条单通道漏斗

我建议你做成下面这个 7 步流程。

---

## Phase 3.6 陌生用户测试漏斗

### Step 1：招募页

页面目标只有一个：

```text
让合适的人留下联系方式
```

内容只要有：

- 这是什么：帮你减少 AI coding 上下文 token
    
- 适合谁：Codex / Claude Code 重度用户
    
- 当前状态：封闭内测
    
- 需要做什么：下载安装、跑一个真实任务、回填反馈
    
- CTA：申请内测
    

不要在这里讲太多架构。

---

### Step 2：资格筛选

你要筛掉不合适的人。

建议只问 4 个问题：

- 你主要用什么：Codex / Claude Code / 其他
    
- 你每周是否真实使用
    
- 你是否在乎 token / 成本 / 上下文效率
    
- 你的系统环境
    

如果他不是目标用户，先不放。

---

### Step 3：发送内测包

给到用户一个**单页入口**，里面只有 4 个东西：

```text
1. 下载按钮
2. 3步安装说明
3. connect 命令
4. 反馈入口
```

不要给他一堆文档。

---

### Step 4：安装与启动

你需要把第一步压到最短。

理想文案：

```text
1. 下载
2. 双击运行
3. 浏览器自动打开 dashboard
```

这正是 Bootstrap 的目标体验：下载 → 双击 → 完成。

如果现实还没完全做到，就老实写：

- Windows：下载 exe，双击
    
- macOS：下载 pkg / app，授权后双击
    
- 第一次打开如果被系统拦截，怎么操作
    

这一步必须有截图。

---

### Step 5：connect

陌生用户最容易死在这里。

所以只给两条命令，不给更多选择：

```bash
omnimemora connect codex
omnimemora connect claude
```

这个命令集本来就是当前 CLI 生命周期的一部分。

并且你要在页面上写清楚：

```text
正常情况下，只需要执行一条 connect 命令
```

再配一个“成功后会发生什么”的说明。

---

### Step 6：真实任务

不要让用户自己猜。

你要给他一个固定动作：

```text
请像平时一样跑 1 个真实任务，持续 10–20 分钟
```

然后告诉他观察两件事：

- dashboard 是否出现 token savings
    
- 你是否感觉使用方式没有被打断
    

这一步不是 demo，而是真实任务。

---

### Step 7：反馈回收

反馈入口必须简单到离谱。

推荐只保留一个：

- Typeform / Tally / Google Form / 飞书表单 / Notion Form 任选一个
    

表单只收这些：

- 是否成功安装
    
- 是否成功 connect
    
- 你觉得这工具是干嘛的
    
- 你信不信 token savings
    
- 你会不会继续用
    
- 卡在哪一步
    
- 联系方式（可选）
    

---

# 陌生用户要跑完全流程，你还需要两个“扶手”

## 扶手 1：状态邮件 / 私信模板

你要在每个阶段给一句话引导。

例如：

### 发包时

“整个过程大概 5–10 分钟，先安装并 connect，然后正常跑一次 AI coding 任务。”

### 24 小时后

“想确认下你有没有跑起来。如果卡在安装 / connect，我这边可以立刻定位。”

### 48 小时后

“如果已经跑过一次，麻烦回填一下 1 分钟表单。我现在主要验证是否真的有价值，不是收好评。”

---

## 扶手 2：故障快速分流

你必须把常见失败做成固定分流：

### A 类：安装失败

- 系统拦截
    
- 权限
    
- 浏览器没自动打开
    

### B 类：connect 失败

- CLI 路径问题
    
- 连接不到 runtime
    
- agent 未识别
    

### C 类：价值感知失败

- 看不懂 dashboard
    
- 不信 savings
    
- 感觉没差别
    

用户一报错，你立刻知道他在哪个桶里，不然你会被支持工作拖死。

---

# 你现在的最优执行方案

我给你压成一句：

## 第一步

先别碰大规模公开发布。  
先做：

```text
官网最小落地页 + 私有下载链接 + 表单申请 + 手动发包
```

## 第二步

先收 5–10 个半陌生用户，跑完整闭环。

等你确认：

再考虑放大到 20–30 人。
